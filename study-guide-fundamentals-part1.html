CHAPTER 1

LLM 기반 의사결정 구조와 에이전트 동작 방식

1.1 – 1.4

1.1LLM은 에이전트의 "두뇌"다

거대 언어 모델(LLM)은 방대한 텍스트를 학습해 다음에 올 내용을 예측하는 모델이다. 이 "다음을 예측하는 능력"이 곧 문제 해결에 필요한 다음 단계를 추론하는 능력으로 확장된다. 에이전트는 이 추론 능력을 활용해 목표 달성을 위한 행동을 계획하고 실행하는 시스템이다 — LLM이 이해·추론을 담당하고, 에이전트는 그 결과로 행동한다.

LLM은 이미 정리된 형태로 판단을 내려주기 때문에 실무 의사결정에도 바로 쓸 수 있다. 다음 두 사례가 대표적이다.

사례 1 · 우선순위 판단
Q다음 에러 로그를 분석해서 우선적으로 수정해야 할 이슈 순위를 알려줘.
A[Critical] DB 연결 시간 초과 — 발생 빈도 532회/24시간, 모든 결제 요청이 실패하는 치명적 이슈. 권장 조치: DB 커넥션 풀 점검, 쿼리 최적화 …
사례 2 · 대안 비교 판단
Q이미지+텍스트 멀티모달 검색을 구현하려 해. 후보는 Pinecone, Weaviate, Milvus, Qdrant야. (요구사항: 약 5억 개 벡터, 200ms 이하 지연, 클라우드 운영, 향후 멀티모달 확장)
A후보별 성능/쿼리속도/운영편의성/비용을 표로 비교한 뒤, 요구사항에 가장 맞는 후보를 근거와 함께 추천.

두 사례 모두 LLM이 객관적으로 정리된 근거를 바탕으로 결론을 내려준다는 공통점이 있다. 에이전트가 여러 단계를 거쳐 작업할 때, 각 단계에서 "다음에 무엇을 할지"를 판단하는 것도 결국 이 능력의 연장선이다.

먼저 알아두기 — 시스템 프롬프트 vs 유저 프롬프트

위 예시의 질문(Q)은 사실 두 겹으로 이루어진다. 시스템 프롬프트는 LLM에게 "당신은 이런 역할이고, 이런 규칙을 따르세요"라고 미리 설정해두는 지침이고, 유저 프롬프트는 사용자가 실제로 입력하는 질문·요청이다.

예를 들어 시스템 프롬프트로 "당신은 사용자의 문의 종류를 파악하는 AI입니다. [주문 조회, 배송 조회, 교환/환불] 중 하나만 선택하세요"라고 미리 규칙을 심어두면, 유저 프롬프트로 어떤 문의가 들어와도 정해진 세 가지 중 하나로만 답하게 만들 수 있다. 에이전트를 설계한다는 것은 결국 이 시스템 프롬프트에 판단 기준을 얼마나 명확하게 담아내느냐의 문제다.

1.3LLM이 다음 행동을 결정하다 — 라우터

쇼핑 플랫폼 챗봇을 생각해보자. 사용자가 "오늘 배송받은 물건에 하자가 있어요, 교환받고 싶어요"라고 입력하면, LLM은 이 문의를 [주문 조회 / 배송 조회 / 교환·환불] 중 하나로 분류해 이후 처리 로직을 결정한다. 이렇게 다음 행동을 선택하는 역할을 하는 요소를 라우터(router)라고 부른다 — 네트워크에서 데이터의 경로를 정해주는 라우터와 같은 개념이다.

같은 원리로 검색 기반 챗봇은 질문 성격에 따라 구글 웹 검색과 사내 규정 검색 중 무엇을 쓸지도 스스로 판단한다. 라우터 개념은 챕터 2의 ReAct 패턴(생각 → 행동 → 관찰)으로 그대로 확장된다 — ReAct는 라우터가 매 순간 어떤 기준으로 다음 행동을 고르는지를 단계별로 보여주는 구조다.

1.4두 가지 설계 방식 — 같은 목표, 다른 제어 수준

"보고서 작성 에이전트"라는 같은 목표도 단계를 누가 정하느냐에 따라 전혀 다른 구조가 된다.

1.4.1 구조의 핵심은 "목차가 이미 주어졌는가"만 판단하면 된다는 점이다 — 목차가 있으면 곧장 목차별 초안 작성으로, 없으면 목차 생성으로 라우팅되고, 이후 흐름은 고정이다. 반대로 1.4.2는 "당신은 주어진 능력을 사용해 알아서 보고서를 작성하는 에이전트입니다"라는 프롬프트 하나로 전체 순서까지 LLM에게 맡긴다.

고정 파이프라인과 자율 루프, 뭐가 다른지 설명할 수 있는가?

CHAPTER 2

AI 에이전트를 구성하는 3가지 핵심 요소

2.1 – 2.4

2.1.1추론 부품 ① — ReAct (생각 → 행동 → 관찰)

2022년 발표된 프롬프트 기법으로, Reasoning(추론)과 Acting(행동)의 합성어다. 문제 해결 순서를 생각하고, 그에 따라 행동하고, 결과를 관찰해 다시 생각하는 과정을 반복하며 최적의 답을 찾는다.

예시 · 100만 행 CSV 매출 분석
Qsales.csv(date, product_id, price, quantity)에서 월별 총 매출과 매출 상위 3개 상품을 구해줘. 100만 행 이상도 메모리 효율적으로.
A생각: 대용량이니 dtype 최적화·필요 컬럼만 로드해야 함 → 행동: dtype·usecols 지정해 CSV 로드 → 관찰: 로드 성공, 메모리 절약 확인 → 생각: price×quantity로 매출 계산 후 groupby 집계 → 행동: 월별/상품별 집계 코드 실행 → 관찰: 결과 출력 확인 → 답: 최적화된 코드와 결과 제시.

2.1.2추론 부품 ② — Reflection (반성을 통한 자기 개선)

답을 바로 내놓지 않고 "왜 그렇게 생각했는지" 근거를 설명하게 해 오류를 줄이는 기법이다. 초안을 만들고, 스스로(혹은 별도 평가 단계에서) 비평하고, 수정 지시를 반영해 다시 쓰는 과정을 목표를 달성할 때까지 반복한다.

예시 · 중복 제거 정렬 함수
Q리스트 중복을 제거하고 오름차순 정렬하는 함수를 작성해줘. 접근 방식, 고려한 점, 개선 가능성까지 근거로 설명해줘.
Areturn sorted(set(numbers)) — 접근: set으로 중복 제거 후 sorted() 정렬 / 고려: 원본 리스트 비변경, 빈 리스트도 안전 / 개선 가능성: 숫자 외 타입 검증 필요, 정렬 옵션 파라미터화 가능.

이렇게 답변 과정에 검토·재평가 단계를 명시적으로 포함시키면, 한 번의 실행으로 끝내는 대신 더 안정적인 결과를 유도할 수 있다.

2.2도구 호출 — LLM의 한계를 보완하다

LLM은 특정 시점까지 학습된 모델이라 최신 정보나 실시간 데이터에 접근할 수 없다. 이를 보완하기 위해 외부 도구(tool)를 사용하도록 하는 것이 도구 호출이다. LLM이 스스로 "이 도구가 필요하다"고 판단해 도구를 선택하고, 실행에 필요한 인자까지 생성한다 — 실제 실행과 결과 반환은 개발자가 시스템에 붙여준다.

학습된 지식만 사용 가능 도구로 능력 확장 (웹 검색·계산·DB 조회…)

도구가 2개 이상이면 "생각" 단계에서 어떤 도구를 쓸지 판단하는 범위가 넓어진다는 점이 다르다. 예를 들어 "오늘 날씨를 바탕으로 옷차림을 애니메이션 스타일로 그려줘"라는 요청에는 웹 검색 도구로 실시간 날씨를 가져온 뒤, 그 결과를 바탕으로 이미지 생성 도구를 다시 호출하는 2단계 ReAct 루프가 필요하다.

도구가 반드시 외부 API일 필요는 없다 — 내부 규칙에 따른 처리 로직이나 사전 정의된 함수도 도구로 추상화해 사용할 수 있다.

2.3메모리 — 대화 맥락과 사용자 이력을 기억하다

에이전트가 자연스럽게 상호작용하려면 지금 대화의 흐름뿐 아니라 사용자의 성향까지 기억할 수 있어야 한다. 챗GPT가 "지금까지 나눈 대화를 바탕으로 내 성격을 추측해봐"라는 요청에 답할 수 있는 것도 메모리 덕분이다.

구분단기 메모리장기 메모리
범위현재 하나의 채팅(세션) 안여러 채팅에 걸쳐 누적
역할대화 흐름·주제를 잊지 않고 유지과거 경험·성향에 기반한 맞춤 응답
필요 시점연속 대화에 대한 피드백을 주고받을 때사용자 취향을 반영하거나 과거 이력이 현재 작업에 영향을 줄 때

2.4종합 — ReAct 기반 LLM 에이전트

추론(ReAct 루프) 안에서 필요할 때마다 도구를 호출하고, 메모리로 대화 맥락을 유지하는 형태로 세 부품이 하나의 에이전트에 결합된다. ReAct 패턴은 가장 기본적이고 유용한 형태로, 챕터 6에서 이를 기반으로 싱글 에이전트를 직접 구현한다.

Chapter 2 체크포인트

ReAct와 Reflection, 언제 판단이 일어나는지 구분할 수 있는가?

ReAct는 행동을 하나씩 실행하면서 그 결과를 보고 다음 생각을 이어가고(진행형), Reflection은 일단 결과물(초안)을 다 만든 뒤 그것을 사후에 비평·수정한다(사후형). 여기에 도구 호출과 메모리가 언제 개입하는지까지 설명할 수 있으면 2장 통과.

CHAPTER 3

목적에 따른 에이전트 아키텍처 설계 기준

3.1 – 3.3

3.1싱글 에이전트 — 하나의 주체가 판단부터 실행까지

싱글 에이전트는 하나의 에이전트가 독립적으로 모든 추론과 행동을 수행하는 구조다. 여러 도구를 갖더라도 판단 주체가 분리되지 않는다는 점이 핵심 — 기획·의사결정·실행을 모두 스스로 담당하는 개인 사업자에 비유할 수 있다.

이 구조의 핵심은 하나의 판단 주체가 여러 능력을 통합적으로 활용한다는 것 — 여러 도구를 오가더라도 판단이 흩어지지 않는다. 업무 자동화 에이전트(계획 수립 → 데이터 가공·작업 수행·알림 전송)도 같은 원리다: 판단이 명시적으로 먼저 오고 실행이 뒤따르는 싱글 에이전트의 또 다른 형태다.

3.2멀티 에이전트 — 판단이 여러 곳으로 분산된다

멀티 에이전트는 여러 에이전트가 각자의 판단을 수행하며 상호작용하는 구조다. 싱글 에이전트를 단순히 여러 개 나열한다고 멀티 에이전트가 되는 것이 아니라, 에이전트 간 의사결정과 정보 교환이 발생하는가가 핵심이다.

구분싱글 에이전트멀티 에이전트
작업 주체하나의 에이전트여러 에이전트
작업 구조공통 목적을 하나가 모두 수행공통 목적을 역할별 하위 목적으로 분담
정보 처리모든 정보를 하나가 종합각자 맡은 부분만, 필요시 서로 전달
확장 방식내부 로직·도구를 확장새 에이전트를 추가

작업이 복잡해질수록 싱글 에이전트는 고려할 정보량이 급격히 늘어 판단의 일관성이 흔들리기 쉽다. 멀티 에이전트는 이 부담을 나눠 맡기는 대신, 소통 비용(정보 누락·왜곡 방지)이라는 새로운 과제를 떠안는다.

3.3어떤 에이전트를 설계해야 할까

에이전트 설계에 절대적인 정답은 없다. 다음 두 기준으로 먼저 판단해보자.

3.3.1싱글 에이전트로 충분한 경우

  • 웹 검색 기반 질의응답 (챗GPT, 퍼플렉시티) — 검색 필요 여부 판단 → 쿼리 생성 → 검색 → 문서 요약 → 답변까지, "실제 웹 정보로 답한다"는 목적 하나로 이어진다.
  • 파일 관리 에이전트 (깃허브 코파일럿) — 파일 생성·수정·삭제·복구를 판단할 때 이전 버전과의 차이, 다른 작업에 미치는 영향을 하나의 맥락으로 관리해야 해서 판단이 분산되면 오히려 불안정하다.

판단 기준: 목적이 하나로 명확하고 · 판단이 하나의 흐름으로 이어지며 · 전체 맥락을 한 곳에서 유지하는 것이 중요하다면 싱글 에이전트가 자연스럽다.

3.3.2멀티 에이전트가 필요한 경우

  • 자료 조사 + 보고서 작성 (릴리스AI류) — 자료 조사 에이전트는 폭넓고 신뢰할 정보 수집에, 보고서 작성 에이전트는 주어진 정보로 문서를 완성하는 데만 집중한다. 판단 기준이 다른 두 역할을 하나에 맡기면 어느 한쪽이 흔들린다.
  • 풀스택 코딩 에이전트 (figma make류) — 프런트엔드(사용자 인터랙션)·백엔드(데이터·API)·디자인(시각적 일관성) 에이전트가 각자 특화된 기준으로 판단하고, 결과를 합쳐 하나의 서비스를 만든다. 실제 개발 조직의 팀 협업과 유사한 구조다.

멀티 에이전트로 갈수록 역할 분리 뿐 아니라 정보 전달 범위와 소통 경계까지 함께 설계해야 한다 — 이 설계 원칙이 7장의 네트워크·슈퍼바이저·계층형 패턴으로 이어진다.

Chapter 3 체크포인트

지금 만들고 싶은 에이전트를 하나 떠올려보자

그 에이전트가 맡을 역할이 하나인가, 여러 개인가? 여러 개라면 역할마다 판단 기준이 서로 상충하는가? "그렇다"고 답할 수 있으면 멀티 에이전트로, 아니면 싱글 에이전트로 시작하면 된다 — 이 스스로 답하는 과정 자체가 3장의 핵심이다.
