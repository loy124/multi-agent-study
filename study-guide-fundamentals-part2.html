CHAPTER 5

랭그래프 기반 에이전트 설계

5.1 – 5.3

5.1왜 랭그래프인가

랭그래프(LangGraph)는 시스템의 로직을 노드(작업 단위)와 엣지(실행 경로)로 이루어진 그래프로 표현하는 프레임워크다. 경로가 복잡한 에이전트도 비교적 쉽게 설계할 수 있고, 반복·병렬 처리 같은 복잡한 제어 흐름까지 명확히 표현한다. 핵심 철학은 "상태 관리" — 작업 중 발생하는 모든 중간 정보와 상태 변화를 그래프 안에서 관리하므로 복잡한 협업도 안정적으로 처리한다. 랭체인(LangChain) 생태계와 통합되어 LLM 호출·도구 사용·메모리 등을 그대로 활용할 수 있다.

다른 프레임워크와의 결

CrewAI

역할 기반 멀티 에이전트에 강점. 여러 에이전트를 "크루" 단위로 묶어 정해진 순서대로 실행 — 책임 구조가 분명한 워크플로에 적합.

AutoGen

마이크로소프트 개발. 에이전트를 팀으로 구성해 그룹 채팅처럼 협업 — 발언 순서·담당을 유연하게 조정.

LlamaIndex

데이터 수집·검색에 강점. 외부 데이터 소스를 LLM이 쉽게 검색·활용하도록 인덱스로 연결.

5.1.1노드와 엣지 — 그래프의 두 재료

노드는 그래프를 이루는 기본 단위(작업 단계), 엣지는 노드 사이의 연결(순서·관계)이다. 엣지는 방향성을 가질 수도, 없을 수도 있다 — "철수는 영희를 좋아한다"처럼 한쪽으로만 향하면 방향 엣지, "철수와 영희는 SNS 맞팔이다"처럼 쌍방향 관계면 방향 없는 엣지로 표현한다.

5.1.2랭그래프를 쓰는 이유는 네 가지다 — ① 여러 단계의 복잡한 로직도 그래프로 구현 가능, ② 노드·엣지 단위로 재설계하기 쉬운 확장성, ③ 조건에 따라 흐름을 나누는 분기 처리, ④ 이전 단계로 되돌아가는 양방향 파이프라인 구성.

5.2기본 개념 4가지 — State · Reducer/Node · Edge · 조건부 엣지

Phase 0 체크리스트에서 "숙지만" 표시해뒀던 개념이 여기서 구체화된다.

① State (상태) — 그래프가 지속적으로 관리하는 데이터 구조. 챗봇이라면 메시지 목록을 messages 키로 관리한다.

# 5.2.1 그래프의 상태 정의하기
from typing import TypedDict

class State(TypedDict):
    messages: list[str]

리듀서(reducer) — 상태가 업데이트되는 방식을 지정하는 함수. 기본값은 "덮어쓰기"지만, Annotated로 리듀서를 지정하면 기존 값에 새 값을 누적할 수 있다. 랭그래프는 메시지 누적용 리듀서 add_messages를 기본 제공한다.

# 5.2.2 리듀서로 메시지를 누적시키기
from typing import TypedDict, Annotated
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]

② Node (노드) — 상태를 입력받아 처리하고, 업데이트할 값을 반환하는 함수. add_node로 그래프에 등록한다.

# 5.2.3 답변을 생성하는 노드 만들기
def chatbot(state: State):
    question = state["messages"]
    answer = f"'{question}'라는 질문을 받았습니다."
    return {"messages": [answer]}

graph.add_node("chatbot", chatbot)

③ Edge (엣지) — 다음에 실행될 경로. 그래프는 반드시 시작점(START)과 종료점(END)을 가져야 한다.

# 5.2.4 시작점 · 종료점과 엣지로 연결하기
from langgraph.graph import START, END

graph.add_edge(START, "chatbot")
graph.add_edge("chatbot", END)

④ 조건부 엣지 — 다음 노드를 조건에 따라 갈라주는 엣지. 라우터 LLM의 판단 결과를 실제 흐름 분기로 연결하는 지점이 바로 여기다.

# 5.2.5 라우팅 함수 정의하고 조건부 엣지 추가하기
def routing_function(state: State):
    if len(state["messages"][-1]) > 1000:
        return True
    return False

graph.add_conditional_edges(
    "chatbot",
    routing_function,
    {True: "summary", False: END}
)

응답 길이·의도 분류 결과 등 라우터 역할을 하는 중간 노드의 출력을 기준으로 다음 행동을 결정해야 할 때 조건부 엣지를 사용한다 — 챕터 1의 "라우터" 개념이 랭그래프 코드로 그대로 구현되는 지점이다.

5.3랭그래프로 에이전트 설계하고 구현하기

지금까지의 요소로 실제 챗봇 그래프를 만든다. 입력 스키마(question)와 출력 스키마(answer)를 상태 전체 스키마(messages)와 다르게 정의할 수도 있다 — 입력·출력에는 최소한의 키만 노출하고, 내부 상태는 더 풍부하게 관리하는 식이다. 이 그래프가 챕터 6 싱글 에이전트 구현의 뼈대가 된다.

6.1, 6.4, 6.5.1

6.4create_agent — 부품을 한 번에 조립

모델, 도구 목록, 시스템 프롬프트를 넣으면 ReAct 루프가 도는 에이전트 그래프를 랭그래프가 바로 만들어주는 조립 함수다. 미들웨어를 추가하거나 구조화 출력을 정의해 세부 동작을 조정할 수 있다.

6.1 · 6.2 · 6.3이 함수를 기반으로 웹 검색 에이전트(타빌리 검색 도구 호출), 코딩 에이전트(코드 실행·파일 저장 도구), RAG 에이전트(벡터DB 검색 도구)를 각각 구현하는 것이 6장 실습의 핵심이다.

6.5.1RAG란 — 검색으로 근거를 보강한다

질문에 답하기 전 벡터DB에서 관련 문서를 찾아 프롬프트에 끼워 넣고, 그 근거를 바탕으로 LLM이 답한다. 모델이 모르는 최신·내부 정보를 다루는 표준 방법이다.

이렇게 완성된 ReAct 기반 싱글 에이전트가 7장 멀티 에이전트의 구성 단위가 된다 — 네트워크·슈퍼바이저 패턴 모두 결국 이런 싱글 에이전트 여러 개를 어떻게 연결하느냐의 문제다.
